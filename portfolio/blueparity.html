blueParity

PROVE A REPLACEMENT SYSTEM STAYS EQUIVALENT WITHIN A DECLARED CONTRACT.

Migration teams comparing an old and a new system usually rely on spot checks and cannot state precisely which behaviors matched, diverged, or were never exercised. blueParity runs both systems as black-box command adapters over the same JSONL corpus under a predeclared, hashed-before-execution equivalence contract, and emits a signed, independently verifiable record of what it found.

REQUEST A PILOT
Runs locally · CLI or web UI · Ed25519-signed certificates · no cloud account required
WHAT IT CHECKS

Both systems run as black-box command adapters over the same JSONL corpus, under an equivalence contract declared and hashed before execution: which outputs matter, what tolerance applies to each, which fields are ignored. Every declared behavior resolves to matched, matched within the declared tolerance, diverged, or not exercised, and every divergence is pinned to a minimal counterexample — the smallest input pair that shows the two systems actually disagreeing.

HOW IT WORKS
1
Wrap both systems. Point blueParity at two command adapters — the legacy system and its replacement — each reading one JSON object per line.
2
Declare the contract. A YAML equivalence contract names the fields that matter, their tolerances, and any fields to ignore, hashed before the run starts.
3
Run the corpus. blue-parity run drives both systems over the same JSONL corpus and produces verdicts with divergences pinned to minimal counterexamples.
4
Write the certificate. blue-parity run --out certificate.json writes the signed bundle — both the declare and result receipts — in the same command. You can also export it from the web interface.
5
Verify offline. The bare receipt checks with verify_receipt.py; the full certificate bundle checks with blue-parity verify.
WHAT IT IS NOT

Equivalence is not correctness. A signed receipt proves what this software ran and recorded; it does not prove either system, or any underlying real-world claim, is correct.

THE RECEIPT
A signed receipt proves what blueParity ran and recorded; it does not prove an underlying real-world claim is true. The certificate binds the equivalence contract, the corpus hash, both adapters' command lines, and every per-behavior verdict — change any one and verification fails. The standalone verify_receipt.py lets a reviewer or auditor check a bare result receipt without installing blueParity; a full certificate bundle verifies with blue-parity verify instead.
GUIDES
Pre-registered vs. post-hoc

A contract hashed and sealed before the corpus is first seen seals as PRE_REGISTERED. Sealing is POST_HOC when a contract is declared against a corpus that has already been first-seen in the same data directory — the first-seen record is never reset by re-uploading identical content.

The four verdicts
  • Matched — field-for-field agreement.
  • Matched within tolerance — within the declared numeric bound.
  • Diverged — the two systems disagreed; a minimal counterexample is attached.
  • Not exercised — the behavior was declared but never triggered by the corpus.
Two verifiers for two artifacts

A bare result receipt (like make demo's output) verifies with the standalone verify_receipt.py. The full certificate bundle downloaded from the web UI — the shape that also proves pre-registration — verifies with blue-parity verify instead. Running verify_receipt.py directly against a bundle correctly reports it invalid; that's the wrong tool for that artifact, not a tamper finding.

SET IT UP

Access first. blueParity is in development and its repository is private today, so there is no public download link yet. Email blue@mobluehq.com and we will grant your GitHub account access to mobluehq-llc/blueparity and tell you the current build. Everything below runs entirely on your own machine afterwards — no account, no cloud service, no API key.

1
Clone it. git clone git@github.com:mobluehq-llc/blueparity.git && cd blueparity
2
Build the environment. make dev creates a local virtual environment and installs blueparity into it. Requires Python 3.12 or newer and Node 20 or newer if you want the web interface.
3
Start the web interface. make serve serves it at http://127.0.0.1:7500, bound to localhost only.
4
Or use the command line. .venv/bin/blue-parity --help lists every command.
5
Working on the interface itself? make dev-api (port 7500) and make dev-web (port 7501) run the two halves separately with hot reload.
IF IT DIDN’T WORK
make dev fails on the Python version

The project requires Python 3.12 or newer, declared in its own pyproject.toml. Check with python3 --version. An older interpreter is the most common cause of a failed first build.

The port is already in use

Every service here binds 127.0.0.1 on a fixed port, and several MOBLUEHQ tools can run at once. Check what holds it with lsof -nP -iTCP:<port> -sTCP:LISTEN and stop that process by its PID. Do not kill processes by name — you may stop something unrelated.

git clone fails with a permission or not-found error

That means your GitHub account has not been granted access yet, or your local git is using a different account. The repositories are private. Email blue@mobluehq.com with the GitHub username you want added.
