blueParity

PROVE A REPLACEMENT SYSTEM STAYS EQUIVALENT WITHIN A DECLARED CONTRACT.

Migration teams comparing an old and a new system usually rely on spot checks and cannot state precisely which behaviors matched, diverged, or were never exercised. blueParity runs both systems as black-box command adapters over the same JSONL corpus under a predeclared, hashed-before-execution equivalence contract, and emits a signed, independently verifiable equivalence certificate.

WHAT IT CHECKS

Both systems run as black-box command adapters over the same JSONL corpus, under an equivalence contract declared and hashed before execution: which outputs matter, what tolerance applies to each, which fields are ignored. Every declared behavior resolves to matched, matched within the declared tolerance, diverged, or not exercised, and every divergence is pinned to a minimal counterexample — the smallest input pair that shows the two systems actually disagreeing.

HOW IT WORKS
1
Wrap both systems. Point blueParity at two command adapters — the legacy system and its replacement — each reading one JSON object per line.
2
Declare the contract. A YAML equivalence contract names the fields that matter, their tolerances, and any fields to ignore, hashed before the run starts.
3
Run the corpus. blue-parity run drives both systems over the same JSONL corpus.
4
Read the certificate. Every rule gets a typed verdict, with divergences clustered and pinned to a minimal counterexample.
5
Verify offline. The bare receipt checks with verify_receipt.py; the full certificate bundle checks with blue-parity verify.
WHAT IT IS NOT

Equivalence is not correctness. A signed receipt proves what this software ran and recorded; it does not prove either system, or any underlying real-world claim, is correct.

THE RECEIPT
A signed receipt proves what blueParity ran and recorded; it does not prove an underlying real-world claim is true. The certificate binds the equivalence contract, the corpus hash, both adapters' hashes, and every per-behavior verdict — change any one and verification fails. The standalone verify_receipt.py lets a reviewer or auditor check a bare result receipt without installing blueParity; a full certificate bundle verifies with blue-parity verify instead.

GUIDES
Pre-registered vs. post-hoc

A contract hashed and sealed before the corpus is first seen seals as PRE_REGISTERED. Re-running the same demo data seals as POST_HOC instead, honestly — the corpus's first-seen record is never reset just because identical content was re-uploaded.

The four verdicts
  • Matched — field-for-field agreement.
  • Matched within tolerance — within the declared numeric bound.
  • Diverged — the two systems disagreed; a minimal counterexample is attached.
  • Not exercised — the behavior was declared but never triggered by the corpus.
Two verifiers for two artifacts

A bare result receipt (like make demo's output) verifies with the standalone verify_receipt.py. The full certificate bundle downloaded from the UI or CLI — the shape that also proves pre-registration — verifies with blue-parity verify instead. Running verify_receipt.py directly against a bundle correctly reports it invalid; that's the wrong tool for that artifact, not a tamper finding.
