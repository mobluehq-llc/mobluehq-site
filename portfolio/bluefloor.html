blueFloor

MEASURE THE INGEST YOUR DEPLOYED DETECTIONS CAN ACTUALLY USE.

SIEM bills scale with ingest. Teams may pay to ingest sources that no deployed detection rule can consume, while cost-cutting exercises sample valuable sources without evidence about which detections depend on them. blueFloor is a local, read-only analyzer: it parses exported detection rules (Sigma / SPL / KQL), maps each rule to the canonical log sources and fields it consumes, joins exported ingest and cost metering, and identifies spend classified as below the deployed detection floor — showing every limitation that prevents classification, and emitting a signed report a third party can verify without installing blueFloor.

WHAT IT CHECKS

Every deployed detection rule — Sigma, SPL, or KQL — is parsed and mapped to the exact canonical log sources and fields it consumes. Each metered source is then classified: consumed by a live rule, partially consumed, sub-floor (no enabled, successfully parsed rule can use it), never evaluated (no ingest row was seen), or cannot-certify (an unresolved parser or mapping gap makes the answer unknown — not the same as unused). A source is only classified as sub-floor once every applicable blocker has been ruled out; an unparsed rule is never assumed to consume nothing.

HOW IT WORKS
1
Export your rules and metering. Sigma, SPL, or KQL rule exports, plus ingest and cost metering exports — nothing connects to a live SIEM.
2
Run the analysis. bluefloor analyze locally, or the same flow through the web UI.
3
Read the source verdicts. Every metered source gets a typed verdict with the reason codes and rule hashes behind it.
4
Inspect a blocker. Open the exact rule or mapping gap keeping a source from being classified below the detection floor.
5
Verify offline. The signed report checks against verify_receipt.py with no SIEM access and no network connection.
WHAT IT IS NOT

blueFloor does not author detections or judge whether a rule is good. SUB-FLOOR means only that no supplied, enabled, successfully parsed rule is proven to consume the source and no unresolved rule can plausibly consume it. It does not mean the source has no forensic, compliance, operational, or future detection value. A signed receipt proves what blueFloor ran and recorded; it does not prove an underlying real-world claim is true.

THE RECEIPT
A signed receipt proves what blueFloor ran and recorded; it does not prove an underlying real-world claim is true. The signature binds the parsed rule set, the source-consumption map, the metering totals, and every per-source verdict — change any one and verification fails. verify_receipt.py is a standalone, dependency-light script, so a counterparty can check the report without installing blueFloor.
GUIDES
What SUB-FLOOR means (and doesn't)

SUB-FLOOR means no supplied, enabled, successfully parsed rule is proven to consume the source, and no unresolved rule can plausibly consume it either. It does not mean the source has no forensic, compliance, operational, or future detection value — that judgment stays with your team.

Reading the six verdicts
  • Consumed — one or more enabled, parsed rules use the source.
  • Partially-consumed — only part of the source's field inventory is proven used.
  • Sub-floor — no enabled parsed rule consumes it, and nothing blocks that finding.
  • Never-evaluated — the source was inventoried but no ingest row was seen.
  • Cannot-certify — an unresolved parser or mapping gap makes the answer unknown.
  • Coverage unknown — the source is consumed by rules, but all of those rules failed to parse. An unparseable rule may depend on this source, distinct from cannot-certify.
Verify a report without installing blueFloor

bluefloor verify path/to/receipt.json — applies the same checks as the standalone verify_receipt.py that ships beside it. Hand that one file to a counterparty and they can check a receipt on a machine with only Python and the cryptography library to verify without any blueFloor installation.

SET IT UP

Access first. blueFloor is in development and its repository is private today, so there is no public download link yet. Email blue@mobluehq.com and we will grant your GitHub account access to mobluehq-llc/bluefloor and tell you the current build. Everything below runs entirely on your own machine afterwards — no account, no cloud service, no API key.

1
Clone it. git clone git@github.com:mobluehq-llc/bluefloor.git && cd bluefloor
2
Build the environment. make dev creates a local virtual environment and installs bluefloor into it. Requires Python 3.12 or newer and Node 20 or newer for the interface.
3
Start the web interface. make serve serves it at http://127.0.0.1:7200, bound to localhost only.
4
Or use the command line. .venv/bin/bluefloor --help lists every command.
5
Working on the interface itself? make dev-api (port 7200) and make dev-web (port 7201) run the two halves separately with hot reload.
IF IT DIDN’T WORK
make dev fails on the Python version

The project requires Python 3.12 or newer, declared in its own pyproject.toml. Check with python3 --version. An older interpreter is the most common cause of a failed first build.

The port is already in use

Every service here binds 127.0.0.1 on a fixed port, and several MOBLUEHQ tools can run at once. Check what holds it with lsof -nP -iTCP:<port> -sTCP:LISTEN and stop that process by its PID. Do not kill processes by name — you may stop something unrelated.

git clone fails with a permission or not-found error

That means your GitHub account has not been granted access yet, or your local git is using a different account. The repositories are private. Email blue@mobluehq.com with the GitHub username you want added.
