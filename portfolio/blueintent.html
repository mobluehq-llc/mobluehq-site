blueIntent

CHECK WHETHER DECLARED CODE INVARIANTS SURVIVED A CHANGE.

A passing test suite doesn't state which declared structural, API, or security invariants an AI-authored change preserved, violated, or left unproven. blueIntent is a CI gate that evaluates a conservative intent.yaml against a base and head revision and emits typed verdicts — PRESERVED, VIOLATED, UNPROVEN, NEVER-EVALUATED, OUT_OF_SCOPE — backed by exact evidence and an offline-verifiable, Ed25519-signed receipt.

REQUEST A PILOT
Runs as a CI gate · CLI or web UI · Ed25519-signed receipts · no cloud account required
WHAT IT CHECKS

A conservative intent.yaml — the invariants a team declares must not silently break, such as a required file staying in place, a forbidden path staying untouched, or a public symbol staying exported — is evaluated against a base and head git revision. Each invariant resolves to one of five typed verdicts, backed by the exact file, symbol, or line evidence behind it. An invariant the engine cannot evaluate — no matching file, an unsupported language, a check outside this version's narrow rule set — is marked unproven or never-evaluated, never silently passed.

HOW IT WORKS
1
Declare your invariants. Write an intent.yaml naming what must not change — required files, forbidden paths, retained symbols, forbidden substrings.
2
Register the repo. Point blueIntent at a local git repository by path; no code leaves the machine.
3
Run the check. blue-intent check --base main --head HEAD --out receipt.json, or wire the same gate into CI with --out to write the receipt file.
4
Read the verdicts. Preserved, violated, unproven, never-evaluated, or out-of-scope per invariant, each with its evidence.
5
Verify offline. blue-intent verify receipt.json or the standalone verify_receipt.py confirms the signed report independent of the CI logs.
WHAT IT IS NOT

This is not formal verification, not a claim of full semantic preservation, and not autonomous code repair.

THE RECEIPT
A signed receipt proves what blueIntent ran and recorded; it does not prove an underlying real-world claim is true. The signature binds the base and head revision hashes, the intent.yaml contract, and every per-invariant verdict — change any one and verification fails. verify_receipt.py lets a reviewer or auditor check the result without installing blueIntent or trusting the CI logs.
GUIDES
The five verdicts
  • Preserved — evidence shows the invariant held.
  • Violated — evidence shows the invariant broke.
  • Unproven — evaluated, but the evidence doesn't settle it either way.
  • Never-evaluated — nothing in this diff touched it.
  • Out of scope — outside what this invariant type checks.
What an intent.yaml can declare today

Required-file retention, forbidden paths, allowed paths, public-symbol retention (Python only in this version), must-contain checks, forbidden-substring checks, forbidden-AST-call checks, JSON-schema-compatible checks, and required-command execution — each a narrow, deterministic rule, not general program verification. Content-scoped checks look at one named file at a time, not a repo-wide pattern.

Wiring it into CI

The same gate that evaluates locally runs in CI against a repo's own intent.yaml. Exit codes are scriptable: 0 for PASS, 1 for HOLD or a failed run, 2 for a usage error.
