blueAlibi

FIND CLAIMS THE RECORDED EVIDENCE AND TOOLS COULD NOT SUPPORT.

AI drafts can assert datasets, trials, institutions, citations, and measured results that the producing run never accessed or performed. blueAlibi is a local claim census: it compares a document against a pipeline's capability manifest and run trace, and marks every claim with a capability-relative provenance verdict.

REQUEST A DEMO
Runs locally · CLI or web UI · Ed25519-signed receipts · no cloud account required
WHAT IT CHECKS

Every factual claim in the document — a cited work, a named dataset, a quantitative result, a claimed action, an institutional reference — is checked against the producing run's own trace of what it accessed, called, and retrieved. A claim that traces to a recorded source is marked supported by provenance. A claim of a kind the run had no mechanism to produce — no experiment tool, no dataset access, no institutional contact in the manifest — is marked unsupportable by construction, and the report names the exact missing capability. A claim with no matching source is marked unsupported, and a claim too vague to check either way is marked unresolved rather than guessed at.

HOW IT WORKS
1
Gather the inputs. A document, a JSONL run trace of what the pipeline actually did, and a YAML capability manifest declaring what it could have done.
2
Run the audit. blue-alibi audit locally, or the same flow through the web UI — no server required either way.
3
Read the claim census. Every claim gets one of four typed verdicts, linked to the evidence at its exact place in the document.
4
Open the trace. Inspect the exact retrieval or tool-call event behind a supported claim, or confirm the manifest gap behind an unsupportable one.
5
Verify offline. blue-alibi verify, or the standalone verify_receipt.py, checks the signed report with no database and no network connection.
WHAT IT IS NOT

Not a global fact checker, not a legal or regulatory opinion, and provenance support does not prove a claim is true. A signed receipt proves what this software ran and recorded — nothing more.

THE RECEIPT
A signed receipt proves what blueAlibi ran and recorded; it does not prove an underlying real-world claim is true. The signature binds the run's input hashes, the capability manifest, every claim verdict, and the evidence list — change any one of them and verification fails. Anyone can check it with the standalone verify_receipt.py script, without installing blueAlibi.

GUIDES
What goes into an audit

Three inputs, all local: the document, a JSONL trace of the producing run's retrievals and tool calls, and a YAML manifest of what that pipeline was actually capable of. Optional source documents let a claim resolve to an exact quoted line.

  • Document: Markdown or plain text.
  • Trace: retrievals, tool calls, datasets touched, measurements taken.
  • Manifest: the tools and data paths that pipeline actually has — never inferred from the trace itself.
The four verdicts

Every claim gets exactly one of four typed states — never a blended score.

  • Supported by provenance — a recorded source could support it.
  • Unsupported, no source — nothing in the trace backs it.
  • Unsupportable by construction — the pipeline had no capability to produce this kind of claim; the missing capability is named.
  • Unresolved — too vague, or the evidence doesn't settle it either way.
Verify a report without installing blueAlibi

A signed report can be checked by anyone with nothing but the receipt file: blue-alibi verify report.json, or hand a counterparty the standalone verify_receipt.py — stdlib plus one crypto library, no server, no account.
