blueAlibi

A LOCAL CLAIM CENSUS · A MOBLUEHQ PRODUCT

AI drafts can assert datasets, trials, institutions, citations, and measured results that the producing run never accessed or performed. blueAlibi is a local claim census: it compares a document against a pipeline's capability manifest and run trace, and marks every claim with a capability-relative provenance verdict.

WHAT IT CHECKS

The deterministic extractor recognizes five claim shapes in a document — Author (Year) citations, named institutions, n=NNN cohort sizes, percentages, and "we ran/conducted/performed…" claimed actions — regex-based and offset-preserving, with no model calls involved. A citation-shaped phrase that names no resolvable author and year (a vague paraphrase like "recent findings suggest…") is still extracted, just marked unresolved rather than guessed at. A document that contains none of these shapes returns zero claims: a clean, correctly-signed empty run, not an error.

THE FOUR VERDICTS

✓ Supported by provenance

A recorded trace event — a retrieval, tool call, or data access the capability manifest actually declares — could support this claim.

? Unsupported, no source

Nothing in the run's own trace backs this claim, even though the pipeline could in principle have produced it.

✕ Unsupportable by construction

The pipeline's own declared capabilities have no tool that could produce this kind of claim — the report names the exact missing capability, in plain language.

… Unresolved

Too vague to check either way — a paraphrase with no resolvable specifics — typed as unresolved rather than guessed at.

The capability manifest is authoritative: a trace event alone can never grant a capability the manifest never declared. Every claim gets exactly one of these four typed states — never a blended score.
HOW IT WORKS
Gather the inputs. A document, a JSONL run trace of what the pipeline actually did, and a YAML capability manifest declaring what it could have done.
The manifest is sealed first. The capability manifest is sealed, signed, and receipted as a DECLARE object before any document or trace is accepted for that run.
Run the audit. blue-alibi audit locally, or the same flow through make serve's local web UI — no server required either way.
Read the claim census. Every claim gets one of the four typed verdicts, linked to the evidence at its exact place in the document.
Verify offline. blue-alibi verify, or the standalone verify_receipt.py, checks the signed receipt with no database, no server, and no account.
WHERE IT ACTUALLY RUNS

blueAlibi runs entirely on your own machine. The CLI never requires a server, and make serve runs the API and the web UI from one local process — not a hosted one. It makes no outbound network calls: the implementation contract behind this product states, as a binding line, "do not add analytics or outbound telemetry," and the shipped UI carries a "LOCAL — no data leaves this machine" chip. There is no billing, authentication, multi-tenancy, or cloud deployment in this product — out of scope by that same contract, not a limitation of this page.

WHAT IT IS NOT

Not a global fact checker, not a legal or regulatory opinion, and provenance support does not prove a claim is true. A signed receipt proves what this software ran and recorded — nothing more. There is also no signer-trust registry yet: verification checks the signature against the public key embedded in the receipt, not against an allowlist of trusted signers — stated at the point of verification, not only in the docs.

THE RECEIPT

Every audit ends in a signed receipt. The signature covers the entire delivered document except the signature and signer key themselves — the capability manifest, the full document text, the run trace, and every claim's verdict — so changing any one of them after the fact breaks verification. Anyone can check it with the standalone verify_receipt.py: standard library plus one crypto library, no server, no database, and no account required.

GUIDES — QUICK READS
What goes into an audit

Three inputs, all local: the document, a JSONL trace of the producing run's retrievals and tool calls, and a YAML manifest of what that pipeline was actually capable of. Optional source documents let a claim resolve to an exact quoted line.

  • Document: Markdown or plain text.
  • Trace: retrievals, tool calls, datasets touched, measurements taken.
  • Manifest: the tools and data paths that pipeline actually has — never inferred from the trace itself.
Try it without your own data — the demo

blue-alibi demo (or make demo) runs a founding-incident scenario: a draft citing two real, retrieved sources, one invented citation, three fabrications each naming a distinct missing capability, and one vague unattributed paraphrase — four verdicts, four distinct reasons. The printed receipt verifies independently against the standalone verifier.

Verify a receipt without installing blueAlibi

A signed receipt can be checked by anyone with nothing but the receipt file: blue-alibi verify report.json (or - for stdin), or hand a counterparty the standalone verify_receipt.py — no server, no database, no account.
