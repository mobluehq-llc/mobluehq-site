bluePipeline

SEE WHAT ACTUALLY REACHED THE MODEL.

Prompt configuration can be edited successfully in one path while a worker resolves a different file, making an intervention appear live when the model never received it. bluePipeline is a Python SDK and local dashboard that records prompt-asset hashes, the assembled prompt, resolver identity, and derived-query provenance for every model call, and signs the result so it can be independently verified offline.

REQUEST A DEMO
Python SDK + local dashboard · Ed25519-signed receipts · no cloud account required
WHAT IT CHECKS

Every model call is instrumented at the SDK level: the hash of every prompt asset actually loaded, the prompt exactly as assembled — after templating, truncation, and tool injection — and, where a derived query is issued, whether it echoes the user's content or the pipeline's own scaffolding. Each call resolves to a typed verdict: the expected config was live, a loaded asset's hash drifted from what the manifest declares, two resolvers can disagree on the same asset, a fragment was duplicated, or a scaffolding string leaked into a derived query — never a dashboard that only shows what the config surface believes is deployed.

HOW IT WORKS
1
Wrap your model client. Install the SDK and wrap the call site — a raw client, LangChain, or a queue worker; three shipped recipes.
2
Get static findings on day one. The resolver analyzer inventories every externalized prompt asset and flags any two code paths that can resolve the same asset differently — no runtime change needed.
3
Every call seals a receipt. At call time, the SDK hashes every loaded asset and captures the final assembled-prompt digest at the last point before transport.
4
Read the findings. The dashboard diffs live hashes against declared config and renders the assembled prompt exactly as sent.
5
Verify offline. bluekit.verify_receipt checks the signed receipt with no server and no model API access.
WHAT IT IS NOT

Not a general LLM observability platform, a model-quality scorer, or an auto-repair tool.

THE RECEIPT
A signed receipt proves what bluePipeline ran and recorded; it does not prove an underlying real-world claim is true. The signature binds the prompt-manifest hash, the assembled-prompt digest, resolver identity, and the call's typed verdict — change any one and verification fails. The standalone bluekit.verify_receipt lets a teammate or auditor check a receipt without installing bluePipeline. A valid signature says who signed; it does not by itself say that signer is trusted.

GUIDES
The verdicts (three live, two defined without live demo paths in v1)
  • Expected config active — the declared prompt assets are what actually loaded.
  • Config drift — a loaded asset's hash doesn't match what the manifest declares.
  • Resolver split — two code paths can resolve the same asset differently.
  • Duplicate fragment — defined but no live demo path in v1.
  • Template leak — defined but no live demo path in v1.

Redaction is opt-in, off by default

Prompt-body capture is off by default; with it off, receipts and traces carry only hashes and structural metadata, never prompt text. Turn it on per project if you need the literal text — redaction patterns for keys, tokens, and emails still apply either way.
