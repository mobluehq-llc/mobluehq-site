Core / application split

The platform is laid out so that core/ (the record engine, receipts, verifier, schemas, and the jurisdiction interfaces) is meant to have zero dependencies on app/ (UI, billing, tenancy, enterprise exports) — clean enough, eventually, to extract a community edition without surgery.

Measured, not assumed: a standing test counts the dependencies running the wrong way, from core into the application layer. That count is 115 today, unchanged across at least two build lanes — a known, open, deliberately-red gap, not a finished boundary. make community does not exist yet in the platform's own Makefile.

The jurisdiction pack model

See the pack spec for the real interface. In short: a jurisdiction is data plus three small adapters (a coding system, a privacy regime, a FHIR profile), never a fork of the core logic. Built so a country is a pack — the US pack is the first. See the mechanism page for exactly what is and isn't wired to it yet — including the single real caller today and the 61 US-only tokens still outside the pack.

Receipts and the verifier

Every product in the commercial suite signs its output with Ed25519 and ships a standalone, dependency-light verifier that checks a signature with no server, no database, and no network connection. Tamper one byte of a signed packet and verification fails. A signed receipt proves what the software ran and recorded — never that an underlying real-world claim is true. This mechanism is the thing the open spine is built around; a ported verifier in another language is expected to be one of the first code contributions once the licence is published.

Nothing on this page is a claim that the split is finished. The 115-dependency count and the single jurisdiction-pack caller are cited so this page can be checked, not taken on faith.
