What's possible now, and what waits on counsel

Open — homeWhyArchitectureSpecContributeFixturesGovernanceSecurityRoadmapCommunity
No real patient, member, claimant or clinician data of any kind — identifiable, de-identified, “anonymised”, aggregated, or screenshot — may be posted, attached, or committed anywhere in this community. Synthetic, generated fixtures only. This covers generated synthetic data only — "de-identified" real data is banned too, because a community has no way to verify a de-identification claim.
The repository is private

There is nothing public to clone or download today. The licence and contribution terms are being decided by counsel; code contributions open when they are published. Until then, contribution means reading, writing, and discussing — not code.

Now
  • File a field report. Tell us what your country's coding system, privacy law, FHIR profile, currency, locale, or payer vocabulary would need to be, using the field-report template. Text only.
  • Read and argue with the design. The specs are written to be read; disagree with a field's shape, and say why.
  • Write a glossary entry. Clinical-term translations for your language are useful now, as text — the string files they'd eventually feed don't exist yet (no i18n scaffold exists in either web app today), so this is groundwork, not a live localisation pipeline.
Later — once the licence and inbound terms are published
  • A jurisdiction pack (a new core/jurisdiction/<xx>/ directory implementing the three Protocols), shipped with a synthetic fixture and passing the interface's own test.
  • A terminology or coding-system adapter — pointing at a national terminology server by URI, never committing a licensed vocabulary's own code tables (CPT, SNOMED) into the repository.
  • A privacy-regime module, reviewed by an in-country reviewer before it is trusted.
  • A ported verifier in another language, checked against the same published test vectors, including the one-byte-tamper case.
