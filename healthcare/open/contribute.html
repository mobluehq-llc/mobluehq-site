What's possible now, and what waits on counsel

Open — homeWhyArchitectureSpecLicensingContributeFixturesGovernanceSecurityRoadmapDownloadsCommunity
No real patient, member, claimant or clinician data of any kind — identifiable, de-identified, “anonymised”, aggregated, or screenshot — may be posted, attached, or committed anywhere in this community. Synthetic, generated fixtures only. This covers generated synthetic data only — "de-identified" real data is banned too, because a community has no way to verify a de-identification claim.
The repository is private

There is nothing public to clone or download today. The licence and contribution terms are being decided by counsel; code contributions open when they are published. Until then, contribution means reading, writing, and discussing — not code.

Now
  • File a field report. Tell us what your country's coding system, privacy law, FHIR profile, currency, locale, or payer vocabulary would need to be, using the field-report template. Text only.
  • Read and argue with the design. The specs are written to be read; disagree with a field's shape, and say why.
  • Write a glossary entry. Clinical-term translations for your language are useful now, as text — the string files they'd eventually feed don't exist yet (no i18n scaffold exists in either web app today), so this is groundwork, not a live localisation pipeline. The product itself stays English-only until that scaffold exists and, for any given language, a named clinical reviewer has signed off — a half-translated clinical screen is a safety question, not a marketing one, so a partial translation is worse than none. Spanish is first in line once that's true. If your country already runs its health system in English, what actually helps adoption is a jurisdiction pack — coding system, privacy regime, FHIR profile — or patient-facing consent text in the local language, not a UI translation.
The single fastest way to help, today

Internally, we've worked one jurisdiction pack as far as general research can take it without a local expert — every field in the pack interface either filled in or marked as an explicit open question, never a guess. That draft alone surfaced eighteen questions that need someone who actually knows that country's health-IT rules, claims process, or privacy-authority practice to answer — not general research, local knowledge. It isn't published here yet (see downloads for what's planned), but the shape transfers to any country: read what a pack needs to answer, pick the fields you actually know the answer to for your country, and send them as a field report. One correct answer to one field is a real contribution today — you don't need the whole pack.

Later — once the licence and inbound terms are published
  • A jurisdiction pack (a new core/jurisdiction/<xx>/ directory implementing the three Protocols), shipped with a synthetic fixture and passing the interface's own test.
  • A terminology or coding-system adapter — pointing at a national terminology server by URI, never committing a licensed vocabulary's own code tables (CPT, SNOMED) into the repository.
  • A privacy-regime module, reviewed by an in-country reviewer before it is trusted.
  • A ported verifier in another language, checked against the same published test vectors, including the one-byte-tamper case.
The developer kit

A developer kit — source, synthetic demo data, and a sandbox to build in — is planned but not written yet; track its status on the downloads page rather than asking here. It will be linked from this page the day it exists, the same rule as the repository itself.

What we will not accept, now or later
  • No LLM anywhere in an extraction or coding path — a model choosing a diagnosis code, a coverage rule, or any clinical fact from free text is exactly the failure mode this project exists to refuse.
  • No clinical content translated without a named clinical reviewer for that language. A fluent, unreviewed translation of a clinical term is a plausible-looking error, which is worse than an obviously missing one.
  • No invented regulatory fact. A field report or a pack that states a country's law or coding rule without saying how confident it is, or where it came from, will be sent back marked NEEDS LOCAL INPUT rather than merged as stated.
  • No patient data, ever — real, de-identified, or "anonymised" — repeating the rule above because it is the one rule that never bends.
  • No feature that lists, browses, requests, or sells data or access to data, in any form, regardless of code quality. This is a scope boundary, not a review comment, and a proposal can be closed on scope alone.
What accepting your code will oblige us to do

Once inbound terms are published, merging a contribution is not a one-time favor to the contributor — it is the company taking on maintenance and security response for that code, indefinitely, and a jurisdiction pack someone contributes may end up configuring a system used on real patients in their country. That is why review is slower than the pull request looks like it deserves, and why a falsifying test is asked of the contributor, not written for them afterward.

How long you'll wait

We can't commit to a response time today — there is no named maintainer yet to hold to one (see community). Say so plainly rather than imply a turnaround we might miss: expect silence to mean "not yet read," not "declined," until a maintainer and a stated reply window exist.
