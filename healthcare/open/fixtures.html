Fixtures

Synthetic fixtures, and the rule that enforces itself

Open — homeWhyArchitectureSpecLicensingContributeFixturesGovernanceSecurityRoadmapDownloadsCommunity
No real patient, member, claimant or clinician data of any kind — identifiable, de-identified, “anonymised”, aggregated, or screenshot — may be posted, attached, or committed anywhere in this community. Synthetic, generated fixtures only.
Why "de-identified" doesn't clear the bar

De-identification, in blueHealthcare's own design, is a receipted, approved, in-institution act. A community has no way to verify a contributor's claim that something was de-identified — so the only enforceable line is generated. This also keeps the hub from ever becoming a dataset exchange by accident.

The pattern this project already uses

The commercial suite's demo posture is the model: an environment flag (BH_DEMO_FIXTURES_ONLY) refuses arbitrary ingest and forces a synthetic-data notice onto every export and UI surface touching demo data — several products already default a project's is_synthetic flag to True. Any future community-edition build is expected to ship with an equivalent lock on by default, so a curious install can't be pointed at real records without a deliberate, documented flip.

A future fixture contribution is expected to carry a marker naming it synthetic and the generator (tool + seed) that produced it — the same shape the repository's own test fixtures already use elsewhere. A pile of files with no generator behind them is the wrong shape for a contribution here, on sight, regardless of content.

Nothing on this page describes a submission mechanism that exists yet — see contribute for what's possible now.
