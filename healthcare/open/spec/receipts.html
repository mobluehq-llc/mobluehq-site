The receipt specification

Draft — v0.1
Open — homeWhyArchitectureSpecLicensingContributeFixturesGovernanceSecurityRoadmapDownloadsCommunity

This page is written for a ministry IT lead, an engineer at another health-software vendor, a security reviewer, or a funder's technical staff deciding whether this is worth attention — not for someone building the blueHealthcare platform itself.

What it is, in one sentence

A way for a clinical or administrative system to hand over a small, signed piece of evidence — "this system did (or refused to do) this specific thing, at this time" — that anyone can check is genuine using nothing but a public key they already trust, with no access to the system that produced it and no need to install any of MOBLUEHQ's software.

Why a country could adopt it independent of this platform

Health systems already have standards for audit logs — a record kept by the system itself of what it did (HL7 FHIR's AuditEvent, IHE's ATNA profile are the well-known ones). What is comparatively rare is a record a system's own operator cannot quietly edit after the fact, checkable by a party that does not trust the operator at all. That property is useful anywhere a health system needs to prove something to someone it does not fully trust and that does not fully trust it back — for example:

  • A national insurer or social-security fund checking that a claims submission matches what a clinic's system actually recorded, without relying on the clinic's own say-so.
  • A donor-funded programme checking that a monthly facility report reflects what a clinic's system held, not what someone typed into a spreadsheet afterward.
  • Any dispute, audit, or legal proceeding where "what did the system actually record, and when" needs an answer that does not rest entirely on the operator's credibility.

You can implement a verifier for this format (checking someone else's receipts) or a signer (producing your own) without adopting any other part of blueHealthcare's software, and — once the licence below is confirmed — without paying MOBLUEHQ anything.

What a receipt does not prove
A verified receipt proves a specific cryptographic key produced specific bytes at a self-declared time. It does not prove the underlying real-world event was true, that the software that produced it was bug-free, or that the key itself was never stolen. The specification document states this about its own format in several places, deliberately — treat any claim that a receipt proves more than that as an overstatement.
Current status

v0.1, draft. One reference implementation exists, used internally across seven of MOBLUEHQ's own products. No implementation by anyone outside MOBLUEHQ exists yet — that is the single biggest gap between this document and something that could honestly be called a standard, and it is stated as a precondition, not hidden: a future version cannot be called v1.0 until at least one outside party has implemented it independently, from the specification and conformance suite alone, with no access to MOBLUEHQ's own source code.

The conformance suite

A specification nobody can check themselves against is just a claim. Alongside the specification document, this project publishes a language-neutral conformance suite: a fixed set of receipts that must verify, and a fixed set of tampered receipts that must not, plus a small runner that can drive any verifier — in any language — through the same test as long as it accepts a file path and trusted public keys and prints a one-line JSON verdict. That means a second, independent implementation, in a different language, having never seen MOBLUEHQ's own code, can prove for itself that it verifies receipts the way the specification requires, rather than taking MOBLUEHQ's word for it.

The vectors are regenerated from the real reference implementation using freshly generated, public-only key material — no private key of any kind is ever committed to the suite, and none of the suite's keys are used by any running instance of the product.

Licensing — read this before building on it

This document does not yet grant anyone a licence to build on it. The licence for this specification layer is a draft sitting with outside counsel and is not yet in effect — the phrase used everywhere in this project's own documentation is "licence: pending legal review." The proposed licence is a real, OSI-approved licence with no country restriction (see the licensing pages for the specific one under consideration), kept separate from the clinical platform, which carries different, country-eligibility-based terms. Until counsel confirms this, nothing here may be described as "open source," and no representation is made that a specific implementation or contribution will be accepted yet. If you are evaluating this for procurement or for a public-goods submission, the honest answer today is: ask MOBLUEHQ directly for current licensing status before relying on anything being freely usable.

Where the specification itself will be published

The full document is not reproduced on this site — it lives in blueHealthcare's own source tree today, alongside its conformance suite, and is not yet published anywhere a party outside MOBLUEHQ can read it independent of the platform's own licence status. A public, versioned home for the document and the conformance suite, separate from the platform's own repository, is expected once the licence question above is resolved. Contact us to ask about early access or to propose a change.
